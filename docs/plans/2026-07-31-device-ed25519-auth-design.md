# CloudSSH 设备码与 Ed25519 设备认证设计

## 目标

Agent Skill 不再依赖长期访问 Token。每台设备首次安装后生成自己的 Ed25519
密钥，通过短期设备码由管理员在网页审批。审批完成后，设备以私钥签名每个请求，
后续不再逐次人工批准。

## 已选方案

采用“设备码 + 网页审批 + Ed25519 请求签名”。未采用长期 Token，是因为 Token
泄露后可在其他设备直接重放；未采用每次人工审批，是因为会破坏持续会话和无人值守
任务；未采用客户端证书，是因为自托管部署的证书签发、轮换和反向代理配置成本更高。

## 数据模型

- `agent_devices`：设备 ID、名称、公钥、指纹、状态、创建/审批/撤销时间、审批人、
  有效期、权限范围、并发限制、最后使用时间和签名计数。
- `agent_device_projects`：设备授权模式为全部可管理项目或指定项目，并保存指定项目关系。
- `agent_device_codes`：只保存设备码摘要、公钥、设备名称、创建时间、过期时间和审批状态；
  明文设备码只在创建响应中返回一次。
- `agent_request_nonces`：保存时间窗口内已用 nonce，或使用等价的有界内存与数据库清理
  机制，阻止请求重放。
- 旧 `agent_tokens` 只保留历史审计。升级迁移后全部撤销，不再参与 Agent 鉴权。

## 首次登录流程

1. Skill 在本机生成 Ed25519 密钥对，并把私钥写入 Windows DPAPI、macOS Keychain
   或 Linux Secret Service；安全存储不可用时直接停止。
2. Skill 仅向平台注册设备名称和公钥，平台返回短期设备码、请求 ID、过期时间与公钥
   指纹。
3. 管理员在“Agent 接入”输入设备码，核对设备名称和指纹，选择所有可管理项目或多选
   指定项目，再设置 scope、并发限制和有效期。
4. Skill 轮询审批结果。获批后只保存设备 ID，不保存任何长期平台 Token。
5. 后续请求均由设备私钥自动签名；设备被撤销、过期、私钥丢失、换设备或轮换密钥时
   才重新走首次审批。

## 请求签名

签名请求包含：

- `X-CloudSSH-Device-ID`
- `X-CloudSSH-Timestamp`
- `X-CloudSSH-Nonce`
- `X-CloudSSH-Body-SHA256`
- `X-CloudSSH-Signature`

签名规范串固定包含协议版本、HTTP 方法、规范化路径与查询、时间戳、nonce 和请求体
SHA-256。服务端验证设备状态、有效期、公钥签名、时间偏差、nonce 唯一性、scope、项目
权限与并发限制。签名和指纹使用无歧义的 base64url/小写十六进制编码。

## 安全边界

- 设备码随机生成、短期有效、单次使用、数据库只存摘要，并限制创建、查询和审批频率。
- 待审批请求不能调用任何 Agent 业务 API，也不能泄露项目、服务器或用户信息。
- nonce 在允许的时间窗口内只能使用一次；时间戳超窗即拒绝。
- 请求体哈希在读取原始字节后校验，避免 JSON 重序列化造成签名歧义。
- 日志、错误响应和审计只记录设备 ID、指纹、请求摘要与结果，不记录私钥、签名原文、
  设备码明文或 SSH 凭据。
- 管理员可查看、重命名、撤销设备；撤销立即影响新请求和租约续期。
- 私钥轮换按新设备审批处理，避免旧私钥为新公钥背书扩大攻击面。

## 兼容与迁移

升级时撤销所有旧 Agent Token，仅保留名称、创建者、历史授权和审计引用；UI 删除创建
Token、复制登录命令和 Token 管理入口，改为设备审批与设备列表。旧 Skill 的 Token 登录
请求返回明确的升级提示，不自动转换成设备身份。

## 测试

- 覆盖设备码摘要、过期、单次消费、并发审批和错误码不泄密。
- 覆盖正确签名、篡改方法/路径/查询/正文、过期时间戳、重复 nonce、撤销和过期设备。
- 覆盖全部项目与指定项目权限、动态失权、scope 和并发限制。
- 使用独立进程验证本机密钥持久化、审批轮询、签名请求、会话续接与登出撤销本地密钥。
- 验证旧 Token 迁移后不可继续访问，历史审计仍可读取。
